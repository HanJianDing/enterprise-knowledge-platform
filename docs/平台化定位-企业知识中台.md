# 平台化定位：企业知识中台

> 2026-10-01 确认的战略定位。面试总结项目时把这个故事放在开头讲。

## 一句话定位

不只是一个 RAG 问答系统，而是**企业知识中台**：知识单点存储、权限统一收口、审计自动留痕，上层各系统按各自权限接入。

## 架构图

```
        ┌─────────────────────────────────────────┐
        │        企业知识底座（本项目）              │
        │  知识存储 · 统一检索 · 部门权限 · 全链路审计  │
        │  对外的门 = MCP server（凭证+库白名单+权限穿透）│
        └──────────────────┬──────────────────────┘
                           │ MCP 接入（每个系统发一把 mcpk_ 钥匙）
        ┌──────────┬───────┴──────┬──────────────┐
     员工问答     IT Agent      财务系统(带沙箱)    未来系统
    （底座自带）  （外部搭建）   （数据分析+业务逻辑） （客服机器人…）
```

## 底座的四项职责（各司其职，不越界）

1. **存知识**：部门分库 + 两层分类树（主题×形态）+ 文档解析分块入库
2. **查知识**：三级检索（子分类→父分类→兜底）+ 混合检索（MMR+BM25 RRF）+ 重排 + Agentic RAG + 知识图谱（在建）
3. **管权限**：部门-库授权矩阵 + 个人覆盖 + fail-closed 检索作用域
4. **留痕迹**：全链路审计（登录/上传/授权/MCP 每次调用，与业务同事务）

## 两扇门（接入能力）

| 门 | 状态 | 给谁用 |
|---|---|---|
| **MCP** | ✅ 已建成 | Agent 类系统：mcpk_ 长期凭证 + 库白名单 + 权限穿透 + 调用审计 |
| **OpenAI 兼容 API** | P0 规划 | 不会讲 MCP 协议的现成框架/第三方工具 |

## 上层系统（领域能力在上层各自实现）

| 系统 | 接入方式 | 领域能力 | 底座提供 |
|---|---|---|---|
| 员工问答 | 底座自带 UI | 聊天/引用来源 | 全部 |
| IT Agent | MCP 凭证（限定 IT 支持库） | 工单联动、外部工具 | 知识+权限+审计 |
| 财务系统 | MCP 凭证（限定财务库+公共库） | **沙箱数据分析**、业务逻辑 | 知识+权限+审计 |
| 客服机器人等 | MCP / OpenAI API | 各业务领域 | 知识+权限+审计 |

## 三个免费红利（上层系统白捡的能力）

1. **知识只存一份**：制度改一次，所有接入系统同步生效；不存在各系统各复制一份知识库的版本漂移
2. **权限统一收口**：发凭证那刻就锁死可见范围（系统级越权不可能）——与部门授权矩阵同构
3. **审计自动继承**：任何系统通过 MCP 查知识，底座自动留痕（谁、什么凭证、查了什么、命中几条），上层系统无需自建审计

## 为什么底座不要沙箱

- 底座职责纯粹：**知识 ≠ 数据**——沙箱算的是"数据"（连数据仓库跑 pandas），MCP 查的是"知识"（制度怎么规定），两者在同一个上层系统里各干各的活
- 底座自身无"不可信代码执行"环节：LLM 零代码执行（算式走 ast 白名单），上传文档只解析不执行
- 隔离技术的正确用法：**演示环境与真实环境物理隔离**（ragdb_demo vs ragdb）就是底座的"沙箱"——风险操作先跑隔离环境，验证后再上真实环境
- 将来底座自带入口若需复杂数据分析，按 P2 上"代码执行工具+沙箱"，属可选演进

## 面试话术

> "我做的不只是一个问答系统，是一个**企业知识中台**：知识单点存储、权限统一收口、审计自动留痕，上层各系统（员工问答、IT Agent、财务分析）通过 MCP 凭证按各自权限接入，领域能力（如沙箱计算）在上层各自实现，底座保持纯粹。这也回答了'企业内部知识库加 MCP 的意义'——它把'一个系统'变成了'一个平台'。"
