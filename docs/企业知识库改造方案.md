# 企业内部知识库改造方案

## 一、背景

现在的系统是「百货通智能客服」：RAG 问答 + 转人工工单 + 反馈看板，已上线运行（Docker 三容器，腾讯云 4核4G，314+87 测试全绿）。你确认的改造目标：

| 维度 | 目标 |
|---|---|
| 规模 | 500 人以上企业 |
| 登录 | 管理员建号/CSV 批量导入 + 密码登录（首登强制改密），预留通用 SSO 插槽（以后有企微/钉钉随时插上） |
| 知识库 | 按部门分多个库 + 精细权限（谁能看/谁能传/谁能管） |
| 上传 | 只有管理员/编辑能传 |
| 客服功能 | 彻底剥离（转人工、工单、坐席、排班全删） |
| 部署 | 先公网，以后可迁内网（预留私有化 LLM 接口） |
| 注册 | 关闭开放注册 |

现状核心短板：只有 admin/user/agent 三个硬编码角色、单一共享知识库、注册完全开放、无部门组织、无审计、无 SSO、提示词全是电商客服话术、Chroma 单实例强制单 worker。

## 二、三个方案对比（你选一个）

### 方案 A：渐进增强（推荐）
**不换技术栈，在现有系统上分阶段加企业能力，每阶段独立上线。**

- 保留 FastAPI + PG + Chroma + Docker 现有骨架和 314 个测试沉淀
- 加：部门组织表、多知识库（向量检索加 kb 过滤）、库级权限、登录体系（建号+密码+SSO 插槽）、审计日志、任务持久化
- 删：客服功能约 1500 行 + 相关表
- 工期 8~10 周，分 7 个阶段，每阶段你能验收一次
- 风险：单 worker 上限（500 人够用）；Chroma 规模上限（预留迁移口，触发信号再迁）

### 方案 B：企业级重构（一步到位）
**按教科书式企业架构重构：Chroma→pgvector、单 worker→多 worker+Redis、硬编码角色→完整 RBAC、任务队列。**

- 工期 12~16 周，重构期内系统无法发布新版，中间没有验收点
- 500 人规模下属于过度设计（角色就 3 个，不需要动态权限表；单机 4核4G 跑不动多实例的意义）
- 结论：不推荐现在做，留作方案 A 的"演进终点"——等出现明确信号（迁内网要 HA、分块 50 万+、统一备份运维）再动手

### 方案 C：借壳开源产品（MaxKB/FastGPT/RAGFlow）
**放弃自研，部署现成产品，把文档迁移过去。**

- 部署 1~2 周见雏形，但部门多库+三权限位+企微+钉钉+审计全对齐需要二次开发或买企业版
- RAGFlow 要 8G+ 内存（现机器跑不动）；丢掉 1.3 万行代码 + 314 个测试的打磨沉淀（逐级下钻检索、RRF 混合检索都是调过效果的）
- 结论：不推荐。你自研这套的面试价值和定制能力都远超借壳

## 三、推荐方案 A 的 7 个阶段路线图

> 每阶段 = 开发 → 测试全绿 → 部署上线 → 你点验 → 答疑 → gitcommit-agent 分阶段提交。阶段间不留半成品。

### 阶段 0（建议尽早办，但不再是卡点）：备案域名 + HTTPS
- **为什么要办**：公网目前是 HTTP 明文，密码登录时密码在传输路上有被截获的风险，上 HTTPS 才安全；另外以后真要插企微/钉钉 SSO，也必须有备案域名（之前把它当卡点就是因为 SSO——现在不接 SSO，它不卡任何阶段了）
- **你要做的事**：腾讯云 ICP 备案（等 2~4 周，等待期间现有 IP 服务不受影响，纯 IP + 密码登录现在就能用）
- **代码侧**：备案下来后 nginx 配证书、CORS 换真实域名
- **验收**：浏览器 https 访问正常、无证书警告

### 阶段 1：多知识库 + 部门 + 精细权限（地基，改动最大，约 2 周）
- **后端**：新表 departments / user_departments / knowledge_bases / kb_members；documents 加 kb_id；[retriever.py](../backend/app/rag/retriever.py) 所有检索入口加**必填 kb_ids 过滤**（不传直接报错，防越权漏过滤——复用现有 category_id $in 的同款写法）；[chat_service.py](../backend/app/services/chat_service.py) 三级检索（子分类→父分类→兜底）全部限定在"用户可见库"内；上传/删除接口带 kb_id + 权限校验；admin 加库/部门/成员管理接口
- **前端**：文档页改多库切换；新增知识库管理页、权限分配页（库 → 授权给部门/个人，勾选读/传/管三项）
- **权限判定规则**（一句话）：个人授权 > 部门授权 > 默认无权限；admin 恒有全部
- **验收例子**：建"人事库"和"财务库"，人事库授权给 HR 部门（可读可传），财务部员工提问时永远搜不到人事库内容；跨部门协作的某个人单独授权后能看到

### 阶段 2：客服功能彻底剥离 + 知识库通用化（约 1.5 周）
- **删代码**：agent 路由、ticket_service（574 行）、human_transfer、工单/排班/心跳三张表模型、require_agent、admin 客服管理段、chat_service 转人工三分支、classifier 的 needs_human/upset、提示词里所有尺码/退货/物流话术
- **数据处置**（你重视数据保留，顺序很重要）：先跑归档脚本把三张表导成 JSON 存档 + 全量 pg_dump + Chroma 目录 tar 双备份 → **你确认收到备份后** → 才执行 drop 表迁移。历史会话里的人工回复消息保留不动；agent 角色用户降为普通用户
- **通用化**：提示词改"企业知识库助手"（报销流程/年假政策/IT 报障/入职材料类示例）；**员工端改为显示引用来源**（文件标题 + 原文片段可点开）——企业知识库和客服的本质区别就是"答案要有出处可查"；无结果文案从"联系人工客服"改为"建议联系知识库管理员"
- **验收例子**：全站找不到客服入口；输入"转人工"不再建工单而是正常问答；历史会话和人工回复记录完好可查

### 阶段 3：关闭开放注册 + 编辑角色 + 管理员建号/批量导入 + 审计日志（约 1 周）
- **后端**：register 接口移除（任何人也注册不了）；管理员创建用户 + CSV 批量导入接口（CSV 含姓名/工号/部门/初始密码，500 人一次导完）；**员工首次登录强制改密**（复用现有改密页）；users.role 收窄为 admin / editor / user 三档，新增 require_editor；audit_logs 表 + 关键操作埋点（登录/建号/改权限/传删文档全留痕）
- **前端**：登录页去掉注册入口；用户管理页加建号/导入；新增审计查询页（按人/按操作/按时间查）
- **验收例子**：审计页能看到"张三 9:30 上传了《考勤制度.pdf》到人事库、李四 9:35 把王五设成了编辑"；editor 能传文档但不能建库不能授权；新导入员工首次登录被要求改密码后才能正常提问

### 阶段 4（可选，等公司有企微账号再启用）：SSO 登录插槽 + 企业微信适配器
- **后端**：设计通用 SSO「插槽」——把"生成授权链接 → 回调换身份 → 绑定或自动建号 → 发 token"的流程抽象成 provider 接口；新表 user_sso_identities（provider/openid 绑定）；企业微信作为第一个 provider 适配器实现（自动建号 + 按企微部门挂到 user_departments + 离职拒登）；登录接口收窄为**仅管理员可用**（管理员密码登录永远保留兜底）
- **前端**：登录页预留扫码入口区（检测到配置了 SSO 才显示）
- **验收例子**：插槽全流程用测试 provider 验证；等有企微账号后填上 corpid/secret 即启用——新员工扫个码，账号自动建好、自动属于他所在部门、直接进聊天页

### 阶段 5（可选）：钉钉/飞书适配器（约 1 周，复用插槽）
- 加钉钉 provider（以后想要飞书也一样），与企微并存互不干扰

### 阶段 6：上传任务持久化 + 收尾与私有化预留（约 1 周）
- **上传修复**：现上传是内存后台任务，重启即丢（文档卡 processing）。改持久化 job 表 + 启动扫描恢复 + 失败重试
- **私有化预留**：LLM/Embedding/Rerank 收敛成 provider 抽象，.env 预留 LLM_API_BASE 等配置——以后迁内网接本地模型（vLLM/bge）只改配置不改代码
- 品牌文案改企业名称；文档列表加"失败重试"按钮

## 四、关键设计决策速览（为什么这么选）

| 决策点 | 选择 | 一句话理由 |
|---|---|---|
| 多库隔离 | 单 Chroma collection + kb_id 元数据过滤 | 员工通常可见 1~3 个库，$in 过滤天然支持多库并集；现有 category 过滤就是同款写法，改动最小 |
| 权限模型 | 部门-库绑定 + 个人覆盖（不做完整 RBAC 三表） | 500 人场景角色就 3 个不会动态增长；表少、规则一句话讲清、审计直观 |
| 向量库 | 保持 Chroma | 500 人峰值并发约 20~50，4核4G 够用 2~3 年；本次把检索收敛成统一入口，迁 pgvector 的成本已降到 3~5 人日 |
| 密码登录 | 全员使用，管理员永远保留 | 当前唯一登录方式（公网必须尽快上 HTTPS 防明文截获）；SSO 插上后员工可改用扫码，管理员密码兜底不撤 |
| 任务队列 | 持久化 job 表，不上 celery/arq | 单 worker 下 job 表半天搞定；Redis+独立 worker 属于方案 B 范畴 |
| 审计 | audit_logs 表 + 十几处显式埋点 | "谁在什么时候动了什么，全部留痕可查"，不用中间件读 body 的复杂方案 |

## 五、风险与应对

| 风险 | 应对 |
|---|---|
| 公网 HTTP 明文传密码有截获风险 | 备案 HTTPS 建议尽早办；迁内网则无此问题；备案下来前不在公网用真实重要密码 |
| 以后插企微/钉钉 SSO 需备案域名+应用审批 | 插槽预留好，等有账号再启用；备案可以提前办掉 |
| 剥离删数据 | 双重备份 + 归档文件交付你确认后才 drop 表 |
| 权限过滤漏掉 → 越权看到别的部门文档 | kb_ids 必填 fail-closed + 权限矩阵单测覆盖"默认拒绝" |
| 对话限频按 IP，企业出口 IP 收敛会误伤 | 阶段 3 改为按用户限频 |
| 离职员工残留权限 | SSO 登录校验在职状态 + 定期对账 |

## 六、整体验证方式

- **每阶段**：后端 pytest 全绿（现有 314 个用例会随剥离增删）+ 前端 vitest 全绿；locust 压测回归；部署到腾讯云后你按验收清单点验（清单写成"打开哪个页面、点哪里、应该看到什么"的操作步骤）
- **端到端验收（全部阶段完成后）**：① 管理员建 3 个库授权给 3 个部门；② CSV 批量导入员工账号，员工首登强制改密；③ 提问只命中本部门库 + 公共库；④ 无权限库的文档检索不到也传不进；⑤ editor 传文档立即生效；⑥ 审计页查到全部操作记录；⑦ 输入"转人工"正常问答不再建单；⑧（SSO 插槽启用后）企微扫码自动建号自动挂部门
- **回归保障**：评估集（检索 60 题/回答质量/裁判式）在阶段 1、2 后各跑一遍，确认改造没有伤到检索效果
